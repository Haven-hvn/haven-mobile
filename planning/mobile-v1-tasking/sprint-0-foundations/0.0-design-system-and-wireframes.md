# Task 0.0 — Design system + v1 wireframes

**Assigned Role:** Product / UI Designer

## Context

Haven Mobile v1 has five user-facing screens (Onboarding, Library, Watch, Community, Settings) and the parity target is `haven-dapp-main`'s web experience — but the mobile app is not a WebView. Every screen needs to be re-thought for Android idioms (Material 3, gesture nav, PiP, lockscreen media controls, SAF). Before any UX Engineer opens a `.kt` file, the visuals and state-to-visual mapping must be **specified** so implementation tasks are unambiguous.

This task runs in **parallel** with the Sprint-0 engineering work. It must land before Sprint 1 UX tasks (1.5 Library, 1.6 Settings, 1.7 Watch) start.

Web reference to draw from (behavior parity, NOT visual parity):
- `haven-dapp-main/src/app/page.tsx` (Onboarding)
- `haven-dapp-main/src/app/library/page.tsx` + `src/components/library/*`
- `haven-dapp-main/src/app/watch/page.tsx` + player component
- `haven-dapp-main/src/app/community/page.tsx`
- `haven-dapp-main/src/app/settings/page.tsx`

## Objective

Produce a design-system spec, a component catalog, and per-screen wireframes with redlines that a UX Engineer can turn into Compose code without design-decision follow-ups. Output can be Figma, Penpot, or Markdown+Mermaid — the format is the designer's call, but every artifact must live under `mobile-app/design/` in the repo (linked/exported PNGs are fine; source Figma URL alongside).

## Interface Contracts

Files that MUST exist under `mobile-app/design/`:

- `mobile-app/design/README.md` — index of everything, plus the brand direction decision.
- `mobile-app/design/tokens.md` — design tokens (color, typography, spacing, elevation, radius, motion). Tokens map to a Material 3 theme that Task 0.2 / Task 1.5 wires up.
- `mobile-app/design/components.md` — component catalog: buttons, badges (`Verified` / `Unverified` / `FailedVerification`, `MediaKind` icons, `ContentCacheStatus` chip), sliders (quota, TTL), transport controls, error/empty/loading panels, viewer chrome (top bar, PiP handle), destructive-action confirmation dialog.
- `mobile-app/design/screens/onboarding.md` — wireframe, state list, redline.
- `mobile-app/design/screens/library.md` — grid+list layouts, search, cache-status chip placement, `MediaKind` icon placement, empty/loading/error states, pull-to-refresh.
- `mobile-app/design/screens/watch.md` — per-kind viewer layouts (video with PiP, audio with lockscreen, image with zoom, PDF paginated, FILE with save/open-with buttons + FR-FILE-3 warning modal).
- `mobile-app/design/screens/community.md` — grouped feed, badge placement, empty state.
- `mobile-app/design/screens/settings.md` — sliders, clear-cache buttons, disconnect confirm, recent-errors panel (Sprint 3 extension shown as an alt layout).
- `mobile-app/design/a11y.md` — accessibility contract: min tap target (48dp), color contrast level (WCAG AA), screen-reader labels for every custom composable, keyboard/dpad support requirements.
- `mobile-app/design/motion.md` — transitions, PiP animation, page-change, chip state changes. Bounded — no gratuitous animation.

## Constraints

- **Material 3 baseline.** Unless there's a strong Haven brand reason otherwise, tokens follow Material 3 defaults. If a custom color palette is chosen, document the accessibility contrast checks.
- **Dark mode by default, light mode supported.** Both light and dark states shown for every screen. Don't skip one.
- **No animation as gate.** Animation must never block interaction. Motion budgets: transitions ≤ 250 ms, media-viewer chrome fade ≤ 150 ms.
- **Empty ≠ loading ≠ error.** Three distinct visual states for every screen that can present them (project Decision 9 makes offline-first UX central).
- **Cache-status chip is a critical primitive.** Library and Community both use it. Design once, reuse.
- **`MediaKind` icons.** One icon per kind (VIDEO, AUDIO, IMAGE, DOCUMENT, FILE) — used as badges in Library/Community and as the primary visual in Watch. Deliver as vector (SVG) so UX can import as vector drawables.
- **Attestation-badge states** (used in Community per FR-UI-3): `Verified`, `Unverified` (no attestation), `FailedVerification` (attestation present but failed). Three visually distinct states — do NOT collapse the latter two.
- **PII in redlines:** no real wallet addresses; use `0xDEAD…BEEF` placeholders.
- **Non-goals compliance** (`MOBILE_V1_REQUIREMENTS.md` §2): do NOT design a chat surface, discovery UI, pay-for-access flow, treasury dashboard, multi-wallet switcher, or notification center. If the designer feels the need to sketch one for context, keep it under `mobile-app/design/post-v1-inspiration/` clearly labeled as out of v1 scope.

## Out of Scope

- Marketing site / Play Store assets.
- App icon (needed for release, but that's a separate small task — file a follow-up if not already covered).
- Motion / animation polish beyond the specified transitions.
- Localization design (English only for v1; RTL support post-v1).

## Acceptance Criteria

- [ ] Every file listed under `mobile-app/design/` above exists.
- [ ] Tokens are concrete values (hex, dp, sp, ms) — not "some blue".
- [ ] Every screen's wireframe shows both light and dark modes.
- [ ] Every screen's wireframe enumerates empty / loading / error / populated states.
- [ ] Component catalog covers every custom composable a UX Engineer will need in Sprints 1–3 (cross-check against the FR list).
- [ ] Accessibility contract enumerates: tap-target min size, contrast level, focus order per screen, screen-reader label rules, dpad/keyboard support.
- [ ] Sprint 1 UX Engineers (Tasks 1.5, 1.6, 1.7) can point to specific artifacts for every design decision they need to implement — verified in the Sprint 1 kickoff.
- [ ] Design review sign-off from the project PM before Sprint 1 UX tasks start.

## Validation Steps

Manual walkthrough with a UX Engineer and the project PM:
1. Pull up each screen's wireframe.
2. For each acceptance criterion in the corresponding Sprint 1/2/3 UX task, confirm the design answers "what does this look like?" without ambiguity.
3. If any UX task's acceptance criterion has no design answer, that's a gap — file it as a design-follow-up before implementation starts.
