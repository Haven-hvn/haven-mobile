# Task 0.2 — Hilt DI bootstrap and `HavenApplication`

**Assigned Role:** Scaffolding Engineer

## Context

Task 0.1 stands up the module graph and wires the Hilt Gradle plugin, but no `Application` class or DI modules exist yet. Haven Mobile v1 uses Hilt across every module (Decision 13). Sprint 0 needs `HavenApplication` in place so downstream tasks can just add `@HiltAndroidApp` collaborators and `@Inject` into their own components without having to touch app-level plumbing.

## Objective

Provide the Hilt entry point (`HavenApplication`) and a stub set of `@Module`s in the `app` module that other tasks will bind into. Establish the DI-composition convention (which module owns which binding) so specialists in later sprints don't have to guess.

## Interface Contracts

- `HavenApplication` class in package `haven.mobile.app`, annotated `@HiltAndroidApp`.
- The `AndroidManifest.xml` in `:app` references `HavenApplication` via `android:name`.
- Convention: **each library module publishes its own `@Module @InstallIn(SingletonComponent::class)` file** under its package root, named `<ModuleName>DiModule`. `:app` does NOT centralize provider bindings — this keeps modules independently testable.
- Coroutine dispatcher provision lives in `:app` (only place with the qualifier types). Provide `@IoDispatcher`, `@DefaultDispatcher`, `@MainDispatcher` `CoroutineDispatcher` bindings using qualifier annotations declared in `:app` package `haven.mobile.app.di`.

## Constraints

- No business logic in `:app` DI modules — bindings only. Real implementations belong in the feature/core module that owns the type.
- Do not add a service locator or fallback. Hilt-only.
- If a module needs a `Context`, use Hilt's `@ApplicationContext` — do not thread a `Context` field through library modules.
- WorkManager: register a Hilt `@HiltAndroidApp`-compatible `WorkerFactory` (via `HiltWorkerFactory`) so later tasks can post workers with `@HiltWorker`. Include the manifest change to disable the default WorkManager initializer.

## Out of Scope

- Any concrete provider (`@Provides fun provideX(): X`) beyond dispatchers.
- Application-level theme (Task 0.8).
- Wallet, cache, canister — those modules are stubs in Sprint 0; their `@Module`s can be empty files.

## Acceptance Criteria

- [ ] `HavenApplication` exists and is registered in `:app`'s manifest.
- [ ] `./gradlew :app:assembleDebug` still passes.
- [ ] Every module in the project has at least an empty `<ModuleName>DiModule.kt` under its package root, annotated `@Module @InstallIn(SingletonComponent::class)`, ready for later specialists to add `@Provides` methods.
- [ ] `IoDispatcher`, `DefaultDispatcher`, `MainDispatcher` qualifier annotations declared and bound in `:app`.
- [ ] `HiltWorkerFactory` bound; default WorkManager initializer disabled in the manifest.
- [ ] Injecting `@ApplicationContext Context` into a scratch `@HiltViewModel` compiles.

## Validation Steps

```bash
./gradlew :app:assembleDebug
./gradlew :app:testDebugUnitTest
```

Optional scratch test: an `@HiltAndroidTest` that starts `HavenApplication` and asserts `HiltWorkerFactory` is injectable. Delete before merge if it churns setup — the assembleDebug is the load-bearing check.
