# Task 3.1 — `core-attestation`: Ed25519 verify + Merkle proof + verification-key cache

**Assigned Role:** Domain Specialist — Crypto

## Context

FR-ACL-3 requires offline attestation verification for community-feed items. Web dApp reference: `haven-dapp-main/src/lib/attestation.ts`. Two verification paths:

- **Single-CID:** an `Attestation` carries an Ed25519 signature over the item's canonical CID. Verify against the canister's cached verification key (fetched via `HavenAol.verificationKey()` in Task 1.4).
- **Merkle-batch:** an `Attestation` carries a Merkle proof plus a signature over the batch root. Verify the proof leaf → root, then the signature over the root.

Failure to verify → the feed item is rendered with an "unverified" badge and (for `FILE`) the SAF export is disabled (Task 2.5 already respects this).

## Objective

Ship `core-attestation` with two verify entry points, a Merkle-proof verifier, and a bridge to `HavenAol.verificationKey()` for the signer key.

## Interface Contracts

```kotlin
package haven.mobile.core.attestation

interface AttestationVerifier {
    /** Verify a single-CID attestation. Returns Result.success(Unit) on pass. */
    suspend fun verifySingle(attestation: Attestation, subjectCid: String): Result<Unit>

    /** Verify a Merkle-batch attestation for the given subject. */
    suspend fun verifyBatch(attestation: Attestation, subjectCid: String): Result<Unit>
}
```

- Hilt binding: `@Singleton` from `haven.mobile.core.attestation.AttestationDiModule`.
- Depends on `HavenAol.verificationKey()` for the Ed25519 pubkey.

## Constraints

- **Offline verification (FR-ACL-3).** After the first fetch of the verification key in a session, verify calls MUST NOT require network. The verifier reads from the cache; only cache-miss reaches the canister.
- **Ed25519 implementation:** use `ic-kotlin`'s crypto module if it exposes Ed25519 (check `ic-crypto-*` modules), else use JDK's `EdDSA` (`java.security` on API 26+). Do NOT pull in BouncyCastle.
- **Merkle-proof hash function:** SHA-256, matches `attestation.ts`.
- **Constant-time comparisons** for signature checks — use `MessageDigest.isEqual` (which is constant-time).
- **Result semantics:** `Result.failure` on any verification failure (signature mismatch, key unavailable, malformed proof). Include a `HavenError` subclass so the UI can distinguish "no key" from "signature failed".
- **Dispatcher:** `@DefaultDispatcher`.

## Out of Scope

- Creating attestations (canister/CLI concern).
- Persisting attestation verification results (in-memory cache is fine; if UI wants to remember "verified" state across sessions, that's a Sprint-3-nice-to-have — not a v1 must-have).
- Merkle tree construction (verification only).

## Acceptance Criteria

- [ ] `AttestationVerifier` at the exact FQCN.
- [ ] Round-trip: sign a fixture in Node/CLI, verify in Kotlin — both single and batch — pass.
- [ ] Fault injection: flip one byte in signature, one byte in proof, wrong pubkey — each returns the correct `HavenError` subclass.
- [ ] Offline scenario: after one canister fetch of the verification key, subsequent verifies work with the transport shut off (mock `IcAgent` throws on every call).
- [ ] Unit test: `./gradlew :core-attestation:testDebugUnitTest` passes.
