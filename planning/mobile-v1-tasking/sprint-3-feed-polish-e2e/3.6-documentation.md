# Task 3.6 — Documentation pass

**Assigned Role:** Documentation Writer

## Context

Haven Mobile v1 needs a coherent doc set before public release: a root README that explains the app, per-module READMEs for the more-load-bearing modules, a `docs/` folder with architecture and perf notes, and — critically — a **parity map** from `haven-dapp-main` to `mobile-app` so a developer familiar with the web dApp can navigate.

Sibling projects already have thorough docs (`foc-local-first-android/README.md`, `ic-kotlin/README.md`) — mimic the tone.

## Objective

Land the v1 doc set at the paths specified below. Content is authoritative-but-brief. No marketing prose; no forward-looking statements about post-v1 features (those live in `FUNCTIONAL_REQUIREMENTS.md`, not in this app's docs).

## Interface Contracts

Files that MUST exist (or be updated) at these paths:

- `mobile-app/README.md` — root README. Overview, quick-start (clone + gradle build), module map, links to sibling projects.
- `mobile-app/docs/architecture.md` — the diagram from `MOBILE_V1_REQUIREMENTS.md` §8 fleshed out with module responsibilities, DI graph, per-wallet namespacing story, plaintext-never-on-disk invariant, hedged retrieval story.
- `mobile-app/docs/parity.md` — table: `haven-dapp-main file → mobile-app module → notes`. Column-for-column with `MOBILE_V1_REQUIREMENTS.md` §3 feature-parity table, but expanded with actual mobile module names.
- `mobile-app/docs/perf.md` — produced by Task 3.4; verify it's present and update prose around the numbers.
- `mobile-app/docs/security.md` — how per-wallet isolation works, what disconnect wipes (order), how plaintext-never-on-disk is enforced, where SAF export is the one exception, threat model summary.
- `mobile-app/docs/ci.md` — the CI story from Task 0.7 + Task 3.5.
- `mobile-app/docs/publishing-migration.md` — how authoring happens (in `haven-cli`, unchanged); v1 mobile is read-only.
- Per-module READMEs at `mobile-app/<module>/README.md` for: `core-domain`, `core-haven-aol`, `core-cache`, `core-cache-mirror`, `core-crypto`, `core-attestation`, `core-security`. Feature-module READMEs are optional.

## Constraints

- **No forward-looking claims.** Do not describe post-v1 features. Do not link to `FUNCTIONAL_REQUIREMENTS.md` except in one place ("this is the v1 subset of…" note, matching the phrasing in `MOBILE_V1_REQUIREMENTS.md` §Status).
- **Command-block accuracy.** Every command shown in a README must actually work at time of writing. Test them.
- **Diagrams:** Mermaid where diagrams are needed. No image files unless a diagram is impossible in Mermaid.
- **Tone:** matter-of-fact, dense-but-scannable. Match `MOBILE_V1_REQUIREMENTS.md`'s voice. No corporate voice.
- **No AUTOGENERATED comments** — this is human-written.

## Out of Scope

- Marketing copy.
- Blog posts, release notes.
- User-facing help docs (Play Store listing, in-app help).
- iOS docs (post-v1).

## Acceptance Criteria

- [ ] Every file listed above exists at the specified path.
- [ ] `mobile-app/README.md` has a quick-start block that a fresh dev can copy-paste to `./gradlew :app:assembleDebug` a working APK.
- [ ] `docs/parity.md` covers all rows from `MOBILE_V1_REQUIREMENTS.md` §3.
- [ ] `docs/security.md` documents the disconnect order from Task 1.8.
- [ ] All command blocks tested and working.
- [ ] Per-module READMEs each have: purpose, public API summary, dependency arrows, gotchas.
- [ ] No mention of post-v1 features (chat, treasury, discovery, publish, iOS) except the one "this is the v1 subset" note.
