# Task 3.5 — Maestro E2E flows + CI wiring

**Assigned Role:** E2E / QA Engineer

## Context

NFR §6 requires "Maestro E2E for: connect → library → watch (video, PDF) → disconnect." Maestro is the chosen tool (matches sample repos in `reown-kotlin-develop/scripts/`, sample `.maestro/` flows in `reown-kotlin-develop/sample/`). This task delivers the flows, the seed data helpers, and the CI hookup.

Reown has known patterns for testing wallet interactions via Maestro (see `reown-kotlin-develop/scripts/run-maestro-pay-tests.sh` and `reown-kotlin-develop/.env.maestro.example`). Reuse them where they fit.

## Objective

Deliver Maestro flows under `mobile-app/maestro/` covering the four v1 acceptance paths, plus a CI job that runs them on every PR.

## Interface Contracts

- Flows live under `mobile-app/maestro/`. One YAML per flow. Flow names use dashes-not-spaces.
- Flow set:
  - `connect-to-library.yaml` — connect wallet → land on Library.
  - `watch-video.yaml` — from Library → tap first video → first frame appears → back to Library.
  - `watch-pdf.yaml` — from Library → tap first PDF → page 1 visible → back.
  - `save-file.yaml` — from Library → tap first `FILE` item → Save to device → confirm warning → verify saved file exists.
  - `disconnect.yaml` — from Library → open Settings → disconnect → verify Onboarding appears.
  - `airplane-mode-cached-playback.yaml` — pre-cache a video → enable airplane mode → play again → first frame within 400 ms budget.
- CI workflow: `.github/workflows/maestro.yml` (or org equivalent) — runs the full flow set on a Firebase Test Lab or emulator matrix. Runs on push and PR.

## Constraints

- **Wallet-connect flow:** use Reown's Maestro pattern from `reown-kotlin-develop/sample/`. Do not deep-integrate with a real wallet in CI — use their test-wallet stub if one exists, or short-circuit `WalletSession.connect()` in a `maestro` build variant with a synthetic address. Document the choice.
- **Seed data:** each flow depends on a specific fixture set (a wallet with known items, a canister with known items). Seed via a `maestro/seed.sh` script that a maintainer runs once per canister redeploy. Do NOT bake canister interactions into the Maestro flow itself.
- **Timing sensitivity:** use Maestro's `waitForAnimationToEnd` and `assertVisible` with timeouts, not hard sleeps. Any `wait` in seconds > 5 is a smell.
- **Flakiness:** each flow must pass 5-out-of-5 on a clean device. If a flow is < 5/5, fix the flow, don't add retries.
- **Screenshots:** each flow captures a screenshot at the "final assertion" step; Maestro artifacts uploaded on CI failure.
- **Coverage of NFR:** the `airplane-mode-cached-playback.yaml` flow is the enforcement mechanism for NFR §6 offline usability + first-frame budget — coordinate with Task 3.4 so measurement/E2E don't duplicate work.

## Out of Scope

- Load testing.
- Flows for post-v1 features (chat, discovery, treasury).
- Cross-app flows (e.g., opening a saved FILE in Google Docs).

## Acceptance Criteria

- [ ] Six Maestro flows committed under `mobile-app/maestro/`.
- [ ] Each flow passes 5-out-of-5 on a Pixel 6 emulator.
- [ ] CI workflow runs the full set on every PR to `main`.
- [ ] Failure artifacts (screenshots, logs) uploaded on CI red.
- [ ] `maestro/seed.sh` documented in `mobile-app/maestro/README.md`.

## Validation Steps

```bash
# Local (assumes an emulator or connected device):
maestro test mobile-app/maestro/

# CI: push a branch that includes these files; observe workflow pass.
```
