# Task 2.4 — `core-haven-aol`: v3 batch decrypt

**Assigned Role:** Domain Specialist — ACL / Haven-AOL

## Context

Haven-AOL v3 metadata (`GateMetadata.V3`) shares one wrapped **gate key** across every item in a gate epoch. Unwrapping once and reusing across items collapses N canister calls to 1 — the whole point of Decision 7. Web dApp references:

- `haven-dapp-main/src/lib/haven-aol/haven-aol-decrypt-v3.ts` — v3 dispatch.
- `haven-dapp-main/src/lib/haven-aol/haven-aol-batch-decrypt-v3.ts` — batch orchestration.
- `haven-dapp-main/src/lib/haven-aol/haven-aol-gate-key-cache.ts` — gate-key LRU behavior.
- `haven-dapp-main/src/lib/haven-aol/haven-aol-v3-cache.ts` — combined gate-key + per-item wrap cache.

Sprint 1's `HavenAol.decrypt` returned `Result.failure` for V3 items. This task makes V3 the primary path and — critically — routes prefetch requests (e.g., "user opened a community feed, warm the top 20 items") through a batch API that issues one canister call per gate epoch.

## Objective

Implement V3 decrypt in `HavenAol.decrypt` and add a batch `decryptAll(items: List<MediaItem>, session): List<Result<ByteArray>>` API for prefetch. Both paths share a single `GateKeyCache` lookup + refill.

## Interface Contracts

Extend the `HavenAol` interface (project README §4.5 remains stable; this method is additive):

```kotlin
interface HavenAol {
    suspend fun decrypt(item: MediaItem, session: WalletSession): Result<ByteArray>
    suspend fun verificationKey(): Result<ByteArray>

    /** NEW in Sprint 2: batch decrypt.
     *  Groups items by (gate, epoch), issues one canister call per group, populates
     *  AesKeyCache for each item, and returns per-item results in the input order. */
    suspend fun decryptAll(
        items: List<MediaItem>,
        session: WalletSession
    ): List<Result<ByteArray>>
}
```

- The single-item `decrypt` for a `V3` item internally calls `decryptAll(listOf(item), session)[0]` — so there is exactly one code path for V3.
- Callers with mixed V1/V3 items pass them to `decryptAll` and the implementation dispatches internally.
- All keys pushed into `AesKeyCache` under `pieceCid` per Task 1.4's invariant.

## Constraints

- **Decision 7:** one canister call per (gate, epoch) group. Verified by an instrumentation test that counts canister invocations via a spied `IcAgent`.
- **`GateKeyCache` reuse:** if the gate key for a group is already in cache and unexpired, skip the canister call entirely. Cache miss → one call per missing group.
- **Ordering:** `decryptAll` MUST return results in the same order as `items`. Do not reorder.
- **Partial failure:** if one group's call fails, items in that group get `Result.failure`; other groups succeed. The whole method never throws.
- **Nonce management:** same policy as v1 (Task 1.4) — one retry on `Nonce mismatch` per group.
- **Signing:** each group's canister call requires one EIP-712 signature. Use `WalletSession.signTypedDataV4` — do NOT collapse signatures across groups.
- **Dispatcher:** `@IoDispatcher`.
- **Coverage floor maintained:** `core-haven-aol` stays at ≥80% line coverage.

## Out of Scope

- Prefetch orchestration UI — the caller (Sprint 3 community feed / library) decides *when* to call `decryptAll`. This task provides the API only.
- Backfilling V1 items into V3 (that's a canister-side concern).
- Per-community "unlock all" UX (post-v1 nice-to-have).

## Acceptance Criteria

- [ ] `HavenAol.decryptAll` at the exact FQCN.
- [ ] `HavenAol.decrypt` on a V3 item returns `Result.success` and the AES key lands in `AesKeyCache`.
- [ ] Test: `decryptAll` on 20 items across 2 gate epochs issues exactly 2 canister calls (verified via spied `IcAgent`).
- [ ] Test: second `decryptAll` on the same items in the same session issues 0 canister calls (all `GateKeyCache` hits).
- [ ] Test: partial failure — one epoch's call throws → its 10 items fail with the same `HavenError`, the other 10 succeed, order preserved.
- [ ] Test: mixed V1 + V3 batch — V1 items fall through the per-item path, V3 items go through the batch path; both populate `AesKeyCache` correctly.
