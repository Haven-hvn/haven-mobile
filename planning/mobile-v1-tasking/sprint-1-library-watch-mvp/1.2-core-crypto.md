# Task 1.2 — `core-crypto`: AES-GCM chunked/streaming decrypt + key caches

**Assigned Role:** Domain Specialist — Crypto

## Context

Haven's content is AES-GCM encrypted; keys are unwrapped by `core-haven-aol` and passed to `core-crypto` for the actual bytes work. The web dApp reference is `haven-dapp-main/src/lib/chunked-decrypt.ts` + `crypto.ts`. Decryption **must never write plaintext to disk** (Decision 2, FR-UI-5) — chunks are decrypted in memory and streamed to the consumer (Media3 for video/audio, Coil for images, PdfRenderer via memory-backed source for PDFs, `ContentResolver`-backed `OutputStream` write in the FILE SAF-export path but *never* an intermediate plaintext file).

Two additional caches live in this module:

- **AES-key LRU** — unwrapped per-piece keys, in-memory only, wiped on disconnect and process death (FR-ACL-2).
- **Gate-key LRU** — v3 dispatch reuses one unwrapped gate key across many items in a gate epoch (parity with `haven-aol-gate-key-cache.ts`).

## Objective

Ship `core-crypto` with (a) AES-GCM decrypt (single-shot for small payloads, chunked/streaming for video), (b) `AesKeyCache` and `GateKeyCache` as memory-only LRUs, (c) a secure-random helper wired to Android Keystore-backed `SecureRandom`, and (d) a `clearAll()` that flushes both caches for the disconnect fanout.

## Interface Contracts

```kotlin
package haven.mobile.core.crypto

/** Chunked/streaming AES-GCM decryptor. Plaintext must never touch disk. */
interface HavenCipher {
    /** Single-shot decrypt for small blobs (thumbnails, JSON, key blobs). */
    suspend fun decrypt(key: ByteArray, ciphertext: ByteArray, aad: ByteArray?): Result<ByteArray>

    /** Streaming decrypt — the returned Flow emits plaintext chunks in order.
     *  Cancellation of the collector must cancel the underlying work.
     *  Framing/format must be compatible with the web dApp's chunked-decrypt.ts output. */
    fun decryptStream(
        key: ByteArray,
        ciphertext: Flow<ByteArray>,
        aad: ByteArray?
    ): Flow<ByteArray>
}

interface AesKeyCache {
    fun put(pieceCid: String, key: ByteArray)
    fun get(pieceCid: String): ByteArray?
    fun clearAll()
}

interface GateKeyCache {
    fun put(gateKey: String, key: ByteArray)
    fun get(gateKey: String): ByteArray?
    fun clearAll()
}
```

- Hilt bindings: all three `@Singleton` in `haven.mobile.core.crypto.CryptoDiModule`.
- Cache capacity defaults: `AesKeyCache` = 256 entries, `GateKeyCache` = 64 entries. Both configurable via `CryptoConfig` injected from `:app`.
- Provide `SecureRandomSource` (a thin wrapper around Android's `SecureRandom`) if any subtask needs randomness — otherwise skip.

## Constraints

- **Decision 2 (plaintext never on disk).** No `File`, `RandomAccessFile`, or `FileOutputStream` in this module. Enforced by code review + a unit test that spy-hooks a temp dir and asserts no writes.
- **AES-GCM parameters MUST match the web dApp's `crypto.ts`:** 96-bit IV, 128-bit tag, IV framed with the ciphertext. Do NOT invent a new framing.
- **`ByteArray` zeroization:** when a key is evicted from either cache, overwrite its bytes with zeros before releasing the reference. Same for intermediate plaintext chunks whose consumer has already accepted them. Zeroization is best-effort in a GC'd runtime — do it explicitly at cache-eviction and `clearAll()` boundaries.
- **Backpressure:** streaming decrypt must not buffer the entire ciphertext in memory. Chunk size follows FR-CACHE-2: 256 KiB.
- **Coroutines only.** No callbacks, no RxJava.
- **No JNI in v1.** Use the JDK's `javax.crypto` — sufficient on API 26+ per `minSdk` target.
- **Dispatcher:** `@DefaultDispatcher` for CPU-bound crypto work; do NOT run on the main thread.

## Out of Scope

- PieceCID / CommP verification (Task 2.6 — that specialist is you too, in Sprint 2, but this Sprint 1 task does not include it).

- Any encryption (v1 is read-only from the mobile app; encryption lives in `haven-cli`).
